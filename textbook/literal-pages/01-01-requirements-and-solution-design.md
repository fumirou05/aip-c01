## まず全体像

Task 1.1は、実装を先に決めるのではなく、事業上の目的、利用者、必要な機能、技術的制約を明らかにし、それらに合うアーキテクチャを設計することを求めている。その設計は小規模な概念実証（PoC）で実現可能性、性能特性、事業価値を検証し、得られた証拠を本格展開の判断に使う。さらに、複数のユースケースや展開先で一貫した実装になるよう、共通部分を標準技術部品として管理する。

AWS Well-Architected Generative AI Lensは、この活動をスコーピングから継続的改善まで続くライフサイクルとして扱う。各段階を、運用上の優秀性、セキュリティ、信頼性、パフォーマンス効率、コスト最適化、持続可能性というWell-Architectedの6本の柱から評価する。

## Skill 1.1.1: 事業ニーズと技術的制約を設計へ結び付ける

公式試験ガイドは、特定の事業ニーズと技術的制約に合う包括的なアーキテクチャ設計を作ることを求めている。設計には、適切なFM、統合パターン、デプロイ戦略などが含まれる。

Generative AI Lensのスコーピング段階では、最初に事業上の問題を理解し、プロジェクトの目標、要件、候補ユースケースを明確にする。高い効果を期待でき、実現可能な用途を選び、関係者の認識をそろえ、成功をどう測るかを定める。この段階では、生成AIがその問題に適切か、既製モデルで足りるか、モデルのカスタマイズが必要か、単一モデルか複数モデルの連携かも検討する。

要件は、必要な振る舞いを示す機能要件と、その振る舞いをどの条件で実現するかを示す非機能要件に分けて整理できる。AWSのPoCガイダンスは、統合を評価するときの非機能要件としてプライバシー、セキュリティ、スケーラビリティ、保守性を挙げ、エンドツーエンドのレイテンシー、1秒当たりのリクエスト数またはトークン数、同時実行数などの性能指標も確認するよう説明している。

| 要件の観点 | 設計前に明らかにする内容 | AWS公式資料との関係 |
|---|---|---|
| 利用者と事業目的 | 誰が、どの問題を解決し、どの事業成果を得るか | スコーピングでは、目標、候補ユースケース、関係者、成功の測定方法を定める |
| 機能 | 入力、期待する出力、対話や処理の流れ、既存システムとの統合 | Task 1.1は事業ニーズに合うFM、統合パターン、デプロイ戦略の設計を求める |
| データ | データの種類、入手可能性、品質、鮮度、利用権限 | スコーピングでは、必要に応じてカスタマイズ用データの可用性と品質を評価する |
| 品質 | 出力の正確性、関連性、一貫性など、用途に必要な水準 | Generative AI Lensは応答品質を、定義済みの正解データまたは利用者の期待に対して測る |
| 性能と可用性 | レイテンシー、スループット、同時実行数、応答可能な時間 | Lensは推論レイテンシー、スループット、応答品質、資源使用率、可用性を主要指標として示す |
| セキュリティとプライバシー | アクセス制御、データフロー、入出力の保護、監査、法令や組織方針 | Lensは安全な通信、最小権限、入出力の無害化、監視を含む境界保護を設計原則とする |
| コスト | Prompt長、データアクセス、モデル、Agent連携などの費用要因 | Lensはスコーピングからコストを検討し、仮定ではなく実測要件で部品を選ぶよう求める |
| データ所在地 | データを保存・処理できる場所と、それに伴うコンプライアンス条件 | Lensのマルチテナントシナリオは、暗号化、アクセス制御とともにデータ所在地への準拠を要件とする |

これらの要件は独立ではない。たとえば、品質を高める追加処理はレイテンシーやコストへ影響し、高可用性のための冗長化はコストや配置へ影響する。そのため、Generative AI Lensは、推測ではなく測定可能な要件に基づいて部品を選び、セキュリティ、性能、コストなどをアプリケーション全体で観測することを設計原則にしている。

## Skill 1.1.2: PoCで仮説を検証する

公式試験ガイドは、本格展開の前に技術PoCを作り、実現可能性、性能特性、事業価値を検証することを求めている。Amazon Bedrockは、その実装に使用できるサービス例として挙げられている。

AWS Prescriptive Guidanceは、PoCを単なる技術デモではなく、次の四つを検証して投資リスクを下げるための実験として位置付けている。

1. 事業価値: 解決したい問題に意味のある効果があるか
2. データ準備状況: 評価やソリューションに必要なデータを、十分な品質と鮮度で用意できるか
3. 技術的実現可能性: 組織の環境で構築でき、必要な統合、性能、セキュリティなどを満たせるか
4. リスク低減: 品質、性能、費用、提供体制などの重大な障害を早期に見つけられるか

PoCでは、事業目標を具体的で測定可能な成功条件へ変換する。品質評価には、対象業務を代表し、専門家が妥当性を確認した評価データが必要になる。性能はレイテンシー、スループット、同時実行数などで測る。品質、レイテンシー、コストには終了条件となる明確な閾値を設け、満たせない場合は方針転換またはPoC終了を判断できるようにする。

PoCの結果は、続行、方針転換、終了の判断に使うだけでなく、当初の事業ケースや機能要件を更新する入力にもなる。

## Skill 1.1.3: 標準技術部品を作る

公式試験ガイドは、複数のデプロイシナリオで実装の一貫性を保つため、標準化した技術部品を作ることを求めている。その手段の例として、AWS Well-Architected FrameworkとAWS Well-Architected ToolのGenerative AI Lensが挙げられている。

Generative AI Lensの設計原則には、Prompt、モデル、アクセス許可などの重要な資源を、集中管理されたカタログと統制で標準化することが含まれる。これにより、セキュリティ、利用統制、バージョン管理、コスト最適化を一貫して扱える。Lensのマルチテナント生成AIプラットフォームシナリオでは、事業部門が個別に同じ仕組みを作らずに済むよう、共通コアサービスや基礎部品を提供する構成が示されている。

| 標準化する関心事 | 公式資料に示される共通化の例 |
|---|---|
| 認証・認可 | ロールおよびユースケース単位のアクセス制御、最小権限、テナント分離 |
| モデルへのアクセス | 複数プロバイダーのモデルへ接続する統一API、モデルカタログ、Gateway、利用上限 |
| Promptと構成資源 | Promptやモデル、アクセス許可のカタログ、統制、バージョン管理 |
| Retrievalとデータ連携 | 再利用可能なデータパイプライン、企業データとの統合用フック、Retrieval-Augmented Generation（RAG）用の部品 |
| Safety | 入力と出力へ一貫して適用するGuardrailとポリシー |
| Loggingと可観測性 | 監査証跡、推論メタデータ、利用量、コスト、性能の監視 |
| Evaluation | 組み込み評価、標準化されたモデル評価フレームワーク、実験の追跡 |

標準化しても、すべての責務が共通基盤へ移るわけではない。マルチテナントシナリオでは、共通基盤が基礎的な統制を提供する一方、データ品質は利用アプリケーションまたはデータ提供者が担い、データドリフトやコンセプトドリフトなどアプリケーション固有の観測も利用側が組み込むとしている。

## Generative AI Lensの現行構成

2026-09-21に確認したGenerative AI Lensは、生成AIライフサイクルをスコーピング、モデル選択、モデルカスタマイズ、開発と統合、デプロイ、継続的改善の順で説明している。各段階をWell-Architected Frameworkの6本の柱に照らし、設計原則、Responsible AI、データアーキテクチャ、Agentic AI、各種シナリオ、柱別のベストプラクティスを収録している。

現行の設計原則は、制御された自律性、包括的な可観測性、資源効率、分散した耐障害性、資源管理の標準化、安全な相互作用境界の六つである。

## 重要な条件と制約

- 設計は、生成AIを使うこと自体ではなく、明確にした事業問題と成功指標から始める。
- PoCは本番システムの代わりではない。事前に定義した仮説と閾値に対する証拠を集め、本格展開の判断材料にする。
- 非決定的な出力を評価するため、対象業務を代表する評価データと、品質の判定方法を用意する。
- 標準技術部品は一貫した統制と再利用を助けるが、アプリケーション固有のデータ品質や運用責任まで自動的に引き受けるものではない。
- FM、統合方式、デプロイ方式、Regionなどの具体的な選択は、要件と検証結果に依存する。Task 1.1だけから一律の構成は決まらない。

| 成功条件 | 測定結果からPoCの続行、方針転換、終了を判断するため、事前に定める基準 |
| 標準技術部品 | 複数のユースケースや展開先で一貫して利用できる、管理されたインターフェース、統制、実装部品 |

- Skill 1.1.2は、PoCで実現可能性、性能特性、事業価値を測り、証拠に基づいて本格展開を判断する。
